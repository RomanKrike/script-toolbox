## Границы изменений

- Схема документов, стабильная версия и ветка `main` не изменяются.
- Независимые изменения порядка и свойств объединяются; несовместимые перестановки вызывают конфликт.
- Неизвестные старые маркеры публикации и повреждённые резервные копии сохраняются для ручного восстановления.
- `load_package` восстанавливает прерванную публикацию под блокировкой: для этого требуется право записи в источник. Если восстановление невозможно, сервис синхронизации сохраняет прежний кэш.
- Остановка планировщика запрещает новые проверки; уже запущенная работа может завершиться.
- Статус страницы библиотеки асинхронный. Создание PresetResolver при открытии Toolbox/редактора и Apply пока синхронное.
- Ошибка построения UI или сохранения не активирует кандидат. После успешной записи ошибка активации переводит окно в диагностический режим с актуальным документом с диска; Reload повторяет построение. Необратимые внешние эффекты внутри пользовательского рендерера не откатываются.

## Проверки

Поведенческие регрессии находятся в `test_document_commit.py`, `test_qt_document_commit.py`, `test_document_index.py`, `test_publication_recovery.py`, `test_qt_audit_runtime.py` и `test_executor_results.py`.

CI запускает новые проверки публикации и Qt на Linux и Windows. Локально используется Python 3.12 / Qt 6 с offscreen-платформой; smoke-скрипты совместимости Python 2 проходят под Python 3 с заглушками Qt. Фактическая совместимость с Python 2.7 проверяется отдельной задачей CI, поскольку локального интерпретатора Python 2 нет.

### B03 — Явный контракт привязки значений

**Цель:** пользовательские типы элементов синхронизируют значения через объявленную привязку; механизм не угадывает устройство их Qt-виджетов.

| Подзадача | Результат | Критерий готовности |
|---|---|---|
| B03.1 | Зафиксировать существующий контракт RuntimeValueBinding и register_value_widget: sync, результат, срок жизни, владелец сигналов | Документированы обновление из модели, изменение из UI, ошибка и удаление элемента |
| B03.2 | Добавить явную регистрацию binding для пользовательского рендерера в существующий конвейер | Пользовательский контрол без стандартного QLineEdit/SpinBox обновляется через свою привязку |
| B03.3 | Перевести встроенные типы на объявленные привязки; поиск контролов оставить только внутри их адаптеров | Каждый встроенный value-item сохраняет прежнее поведение; для custom-item нет эвристического поиска |
| B03.4 | Определить освобождение привязок и сигналов при замене, rebuild и закрытии | Старый binding не получает обновлений; повторная регистрация не удваивает обработчики |
| B03.5 | Добавить пример расширения и проверки двусторонней синхронизации | Изменение из скрипта и UI сходится к одному значению, без рекурсии сигналов; ошибка binding диагностируется |

Основные места: `ui/runtime_value_sync.py`, `ui/runtime_renderers.py`,
`core/runtime_registry.py` и документация расширений.
Приоритет: высокий; выполняется первым, чтобы определить правила владения для B02.
Прикладной API работы с item и JSON-схему без необходимости не менять.

### B02 — Безопасная активация интерфейса

**Цель:** ошибка пользовательского рендерера при Apply не оставляет частично построенный интерфейс и не теряет правки редактора.

| Подзадача | Результат | Критерий готовности |
|---|---|---|
| B02.1 | Описать состояния prepare / persist / activate / dispose и владельцев документа, виджетов, индексов и bindings | Для каждой границы определено состояние после ошибки; нет обещания общей атомарности диска и Qt |
| B02.2 | Подготовить кандидат UI в изолированном владельце на GUI-потоке до записи документа | Рендерер, упавший на первом или последующем элементе, не меняет активное окно и файл |
| B02.3 | Удалять ресурсы неудачного кандидата, включая зарегистрированные callbacks и bindings | Повторный Apply после ошибки не оставляет подписок, виджетов и активных таймеров |
| B02.4 | Сохранить подготовленный документ с проверкой ревизии, затем активировать готовый UI без повторного вызова рендереров | Ошибка записи или конфликт ревизии сохраняют прежний UI и staged-правки; успешный Apply активирует именно сохранённый кандидат |
| B02.5 | Определить восстановление при исключении после успешной записи | Ошибка видна пользователю; приложение восстанавливает согласованное состояние из актуального диска, не затирая конкурентные изменения |
| B02.6 | Сохранить состояние окна при успехе и добавить инъекции ошибок на границах | Выбранный таб и допустимые позиции прокрутки сохраняются; проверены состояние редактора, references, индексы и отсутствие дублей сигналов |

Основные места: `ui/debounced_main_window.py`, `ui/main_window.py`,
`ui/editor_document_adapter.py`, `ui/runtime_renderers.py` и `core/config_store.py`.
Приоритет: высокий; зависит от B03.1–B03.4.
Создание QWidget остаётся на GUI-потоке. Рендереры должны создавать UI без выполнения пользовательских действий и необратимых внешних побочных эффектов; ограничения необходимо документировать.

### B01 — Фоновая подготовка снимков пресетов

**Цель:** открытие Toolbox/редактора и подготовка Apply не блокируют GUI загрузкой и проверкой больших локальных библиотек.

| Подзадача | Результат | Критерий готовности |
|---|---|---|
| B01.1 | Измерить чтение, проверку пакетов, поиск targets и разрешение references на воспроизводимой большой библиотеке | Есть baseline времени по стадиям и задержек GUI; измерения используют тестовые файлы |
| B01.2 | Отделить загрузку и проверку снимка от PresetResolver и построить индекс targets | Снимок готовится без Qt и без изменения живого документа; повторный target lookup не обходит весь пакет |
| B01.3 | Добавить фоновую подготовку с идентификатором запроса и поколением источников | Результат для устаревшей конфигурации источников или закрытого окна игнорируется |
| B01.4 | Подключить снимок к открытию Toolbox и редактора с явными состояниями загрузки и ошибки | GUI продолжает обрабатывать события; reference не создаётся из ещё неготового снимка; прежний валидный снимок сохраняется при ошибке обновления |
| B01.5 | Подключить подготовку к Apply, сохранив проверку актуальности документа перед commit | Изменения runtime за время подготовки проходят трёхстороннее слияние; конфликт не записывает устаревший кандидат; UI строится только на GUI-потоке |
| B01.6 | Проверить медленный диск, большой пакет, повреждённый кэш, смену источника и закрытие окна | Нет применения устаревшего результата и callback к уничтоженному окну; целевой предел задержек GUI выбран по baseline и проверен |

Основные места: `core/preset_references.py`, `core/preset_sync.py`,
`ui/managed_presets.py`, `ui/preset_hooks.py` и путь Apply.
Приоритет: средний; B01.1–B01.2 можно готовить независимо, интеграция B01.5 зависит от B02.
Снимок закрепляется за операцией/окном явно; запрещено менять используемый снимок из worker-потока.
