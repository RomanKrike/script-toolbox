| Review item | Change |

## Rollout and remaining work

- A portable installation with the old launcher needs **one manual replacement** with the recovery-capable build. Automatic replacement is refused when the current build does not advertise recovery support. Otherwise a crash during the first migration could leave a launcher unable to perform recovery.
- `standalone-update-status.json` records helper outcome. Recovery and failed application are shown on the next startup. A rollback that fails preserves its backup and journal for retry after files become available.
- Files removed in a new version are deleted only when the previous manifest owns them. Unknown files in shared installations are preserved.
- Public update entry points hold the installation lock. The low-level UpdateTransaction class is a transaction primitive; callers using it directly must hold that lock.
- The final editor is now declared in `ui/composed_editor.py` with cooperative controller, reference, preset, template and telemetry mixins. Legacy factories remain compatibility APIs for custom views; normal startup does not execute them. The unreachable snapshot-history implementation is removed from the base view.
- Production discovery now runs in a read-only subprocess with a 15-second deadline and cancellation on page destruction/application shutdown. It uses the shared portable Python or a local Python/mayapy/hython interpreter; embedded hosts without such a runtime report an actionable error instead of falling back to an unbounded scan. Profile-root add/remove validation now uses application-owned workers as well.
- Maya uses the shared managed-file helpers. Duplicate complete blocks are normalized; orphaned/nested markers refuse writes and report a broken integration. Package download/checksum/extraction/metadata primitives now live in `core/update_package.py`; plugin and portable installers import that API. Older updater helper imports remain aliases for compatibility.
- The native launcher recovery path preserves the existing application ID, in-process Python startup, icon and pinning behavior. It only starts an external process when a pending update needs recovery.

## Discovery and update follow-up

- Discovery uses an isolated read-only interpreter, bounded polling and process cancellation; it never imports host APIs from the package. Snapshot transport preserves profile IDs, status and options. A local interpreter is required; network-hosted executables are not probed automatically. Maya/Houdini interpreter startup and Nuke/shared portable runtime selection still need real host acceptance.
- Development plugin and standalone builds complete independently before the publication job starts. That job validates both package versions/checksums, uploads immutable versioned archives, then legacy aliases, and publishes the manifest last. New clients use manifest-pinned assets. Old clients that ignore the new manifest fields still use mutable aliases and retain a brief compatibility publication window; checksum/version guards continue to reject mismatches safely.
- Native restart uses .NET process creation rather than Start-Process, clears inherited Python path/home variables, retries immediate process exits and waits for a token acknowledgement written after the new UI window is shown. A committed installation is preserved when restart fails, and the status file records the separate restart result. New builds advertise handshake support; recovery of older builds uses a process-liveness fallback.
- Windows coverage now includes actual child executable launch and failure, and a packaged native EXE update/restart smoke with real Python/Qt. The original user restart incident had no retained diagnostic, so its exact cause is not retrospectively asserted.
- The running updater creates the helper before replacing itself; the new restart protocol applies to updates initiated from this or a later build.

Local checks: 702 unit tests passed (15 platform/Qt skips), 9 real Qt subprocess tests passed; lint and compileall passed. Remote acceptance results are recorded in the PR.

Remaining acceptance: real Maya/Nuke/Houdini sessions, mapped/UNC custom roots, multiple installed Python generations, and Windows taskbar/pinning. Installation/profile-mutation workers are not forcibly terminated during writes.

## Concurrent installer acceptance follow-up

- Exercise the public plugin installer in two independent Python processes against one installation root, downloading a real ZIP and SHA-256 file from a loopback HTTP server.
- Pause the first process after durable prepared/backup_moved journal writes. The competing installer must fail before downloading or recovery, preserving the journal, staged bytes and live/backup directory state.
- Kill the owner after backup_moved, then use a fresh public installer to verify lock release, recovery and successful installation with complete artifact cleanup.
- Run these cases on Linux and Windows. Synchronization pauses wrap actual journal writes; download, checksum verification, extraction, recovery and activation use production code.
- A real Windows portable helper paused during apply also excludes the public plugin installer before download/recovery. A discovered empty-file interoperability bug is fixed: Python no longer writes a sentinel before acquiring the byte-range lock, and failed acquisition cleanup preserves FileLockError and releases the local guard.
- Tests verify that the same process can acquire the lock after the helper finishes. Simultaneous real DCC sessions remain manual acceptance.
