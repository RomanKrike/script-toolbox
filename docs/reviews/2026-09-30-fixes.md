# Architecture review remediation

Base: `dev` at `925b4483c093743ca40a0e2346be2742d3c7fdad`.

## Implemented

| Review item | Change |
| --- | --- |
| 1. QThread lifecycle | Application-owned update/scan jobs survive deletion of a window. Closed windows disconnect update results. Normal close/reload is refused during installation; process shutdown waits for commit completion without terminating threads. |
| 2. Concurrent update | UI rejects duplicate installs. An OS-owned byte/file lock covers plugin recovery/staging/activation and portable staging/application. Process crashes release ownership; persistent lock files must not be deleted. |
| 3. Portable replacement | Explicit file ownership manifest; per-file backup, atomic replacement, durable phase journal, rollback and next-launch native recovery before loading runtime DLLs. Helper reports staging separately from installation and writes a result file. |
| 4. Preferences | Same-directory temporary file, flush/fsync, atomic replacement, atomic backup, corruption preservation and recovery. Loaded snapshots merge only locally changed keys into the current settings inside a lock. |
| 5. Stale configuration | Loaded documents carry a private hash revision. ConfigStore checks its revision inside the same lock as backup rotation/save. Conflicts retain the live file and write a separate local copy. Reload refreshes the revision. |
| 6. Public window | A declared final class with a static MRO is shared by public imports, DCC and standalone launch. |
| 7. UI mutation | Constructor/selection/state/value/trigger/scroll/folder patches are replaced by ordinary methods, mixins and constructor calls. Share factory is injected, and the base editor module export is not reassigned. Runtime renderer decorators remain explicit registry extensions. |
| 8. Qt mutation | Private Qt namespaces and a local regex adapter preserve legacy names without altering PySide modules/classes. Modal execution uses a helper. Known hosts do not silently probe another Qt major. |
| 9. Nuke profiles | Startup records the active profile; live sync checks it before applying another profile. Existing startup calls remain supported. |
| 10. Behavioral coverage | Real QApplication subprocess tests cover close/delete during update, duplicate install/close guard, editor/reload, runtime value/folder behavior and a slow settings scan. Windows PowerShell tests exercise successful apply, partial-write failure, killed helper recovery and a locked DLL. |
| 11. Responsive settings | Detection/status reads and single/bulk integration installation run outside the UI thread; live host API calls remain on the main thread. |

## Rollout and remaining work

- A portable installation with the old launcher needs **one manual replacement** with the recovery-capable build. Automatic replacement is refused when the current build does not advertise recovery support. Otherwise a crash during the first migration could leave a launcher unable to perform recovery.
- `standalone-update-status.json` records helper outcome. Recovery and failed application are shown on the next startup. A rollback that fails preserves its backup and journal for retry after files become available.
- Files removed in a new version are deleted only when the previous manifest owns them. Unknown files in shared installations are preserved.
- Public update entry points hold the installation lock. The low-level UpdateTransaction class is a transaction primitive; callers using it directly must hold that lock.
- The editor still uses controller/preset/reference/template/telemetry subclass factories. They no longer depend on the removed module/class mutations, but consolidating them into a single declared editor class and deleting unreachable legacy history code remains a separate architecture task.
- A worker keeps the settings UI responsive, but Python cannot safely interrupt an arbitrary blocked OS filesystem call. Shutdown may wait for a stalled network filesystem. Strict discovery deadlines require a separately killable discovery process suitable for each embedded DCC/portable runtime. Profile-root add/remove validation is still synchronous.
- Maya managed-file duplication and updater download/verify helper extraction are not part of this patch. They need their own malformed-marker and compatibility tests.
- The native launcher recovery path preserves the existing application ID, in-process Python startup, icon and pinning behavior. It only starts an external process when a pending update needs recovery.
